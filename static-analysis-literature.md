## [Do code LLMs do static analysis?](https://link.springer.com/article/10.1007/s10664-026-10853-z)
- https://github.com/apcl-research/llm-reason
- "We found that LLMs show poor performance on static analysis tasks and that pretraining on the static analysis tasks does not generalize to better performance on the code intelligence tasks and vice versa."
- AST, call graph, data flow graph generation by prompting (and finetuning) an LLM
- static analysis in this paper means the human programmer mental model understanding of code, not formal verification method
- "For example, we found that LLMs tend to predict more cycles than it actually has in the callgraph. The possible explanation is that cycles are more straightforward for LLMs to predict than predicting indirect edges. This would further show that LLMs are lack of semantic reasoning skills and guide future research to develop new model architectures and training procedures to help LLMs to learn the semantics of inputs."
- "Overall, we found that LLMs do not use static analysis like a human would."

## [Helping LLMs improve code generation using feedback from testing and static analysis](https://link.springer.com/article/10.1007/s44163-026-01009-5)
- "Our results show that models often produce incorrect code, and that the generated code can include safety issues. Moreover, they perform very poorly at detecting either issue. On the positive side, we observe a substantial ability to fix flawed code when provided with information about failed tests or potential vulnerabilities, indicating a promising avenue for improving the safety of LLM-based code generation tools."
- "We provide a fully automated, modular pipeline requiring minimal human intervention, easily extensible to other models and analyzers. Code and data are availablenull [sic] at https://doi.org/10.6084/m9.figshare.26984716."
- "Furthermore, our findings indicate that LLMs exhibit a very low degree of self-awareness about the correctness and safety of their generated code. On the other hand, when prompted with issues, on both safety and correctness, these models show some capabilities of repairing the code they or other models have produced."

## [Guiding Symbolic Execution with Static Analysis and LLMs for Vulnerability Discovery](https://arxiv.org/abs/2604.06506)
- "SAILOR operates in three phases: (1) static analysis identifies candidate vulnerable locations and generates vulnerability specifications; (2) an LLM uses vulnerability specifications and orchestrates harness synthesis by iteratively refining drivers, stubs, and assertions against compiler and symbolic execution feedback; symbolic execution then detects vulnerabilities using the generated harness, and (3) concrete replay validates the symbolic execution results against the unmodified project source."
- "We evaluate SAILOR on 10 open-source C/C++ projects totaling 6.8 M lines of code. SAILOR discovers 379 distinct, previously unknown memory-safety vulnerabilities (421 confirmed crashes)."
- https://github.com/shafiuzzaman-md/STAILOR

## [Persistent Human Feedback, LLMs, and Static Analyzers for Secure Code Generation and Vulnerability Detection](https://ieeexplore.ieee.org/document/11500264)

## [Execution-State-Aware LLM Reasoning for Automated Proof-of-Vulnerability Generation](https://arxiv.org/abs/2602.13574)
- https://github.com/learjet5/DrillAgent 
- agentic framework for proof-of-vulnerability (PoV) iterative generation
- PoV is the concrete input that deterministically triggers the vuln
- "This paper presents DrillAgent, an agentic framework that addresses the challenge of automated PoV generation by bridging the gap between static semantic reasoning and dynamic execution. Unlike prior approaches that rely on blind mutation or open-loop generation, DrillAgent formulates the task as an iterative hypothesis–verification–refinement process."
